# 16 倍异常根因排查报告

> 日期：2026-09-22
> 背景：Sol 审阅后要求「在根因没找出来之前，不再比较滤波器优劣」
> 结论：**已定位到最可能的根因，且是我自己的代码 bug，不是相机问题**

---

## 1. 异常现象

同一个「30fps 848x480 无滤波」配置，两次独立运行得到：

| 运行 | 脚本 | 0-300mm MDR | 漂移 |
|---|---|---|---|
| A | `rs_filter_compare.py` | **45.015 mm** | 30.807 mm |
| B | `rs_mdr_probe.py` | **2.756 mm** | 0.933 mm |

相差 **16 倍**。且运行 A 的漂移（30.8mm）同样异常。

---

## 2. 排查过程：意外发现一个 API 陷阱

在按 Sol 建议做「同一份 raw 数据用多套逻辑分析」时，采集脚本反复报：

```
RuntimeError: Frame didn't arrive within 10000
```

而单独的最小测试完全正常。逐步二分后定位到一个**反直觉的 API 行为**：

### 2.1 实测证据

```
=== 测试1: 枚举 option 但不读取值 ===
  枚举 25 项（不读值）
  ❌ 失败: Frame didn't arrive within 8000

=== 测试2: 只读取 safe 的 option ===
  exposure=8500.0
  gain=16.0
  laser_power=150.0
  ✅ 仍能出帧
```

**结论：在 pipeline 运行期间调用 `sensor.get_supported_options()` 会阻塞帧流，
即使完全不读取任何 option 的值。**

而逐个读取已知 option（`get_option(rs.option.xxx)`）是安全的。

### 2.2 为什么会这样

推测机制：`get_supported_options()` 在 D400 系列驱动实现中会触发一次
**sensor 状态查询/重协商**，该操作与帧采集线程争用同一互斥量，导致帧流停摆。
这与我们在 macOS 上观察到的 `mutex lock failed` 异常属同类问题。

（这是实测观察 + 合理推测，未在 librealsense 源码中逐行确认。）

---

## 3. 根因假设链

`rs_filter_compare.py` 的 `main()` 开头有以下代码：

```python
pipe = rs.pipeline()
cfg = rs.config()
cfg.enable_stream(rs.stream.depth, 848, 480, rs.format.z16, 30)
p = pipe.start(cfg)                          # ← pipeline 已运行
ds = p.get_device().first_depth_sensor()
opts = ds.get_supported_options()            # ← 阻塞帧流！
pipe.stop()                                  # ← 在阻塞状态下停止
```

完整因果链：

```
1. main() 启动 pipeline 后立即调用 get_supported_options()
2. → 帧流被阻塞，该 pipeline 收不到帧
3. → pipe.stop() 在异常状态下执行，USB/sensor 状态可能未干净释放
4. → 紧接着矩阵测试的第一个配置（"30fps 848x480" 无滤波）继承了这个污染状态
5. → 该配置得到 MDR = 45.015mm（异常）
6. → 后续配置因新的 pipeline 重建而恢复正常
```

**这完美解释了为什么只有「排第一的无滤波配置」异常**，而同一矩阵里
后续的 temporal / HighAccuracy 等配置都正常 —— 它们运行在新的 pipeline 上。

而 `rs_mdr_probe.py` 没有这个调用，所以拿到正常的 2.756mm。

---

## 4. 修复

### 4.1 已修复

`rs_filter_compare.py` 中的预设枚举改为**硬编码常量**，不再调用
`get_supported_options()`：

```python
presets = {
    "default": None,
    "high_accuracy": 3,     # D400 预设编号：3 = HighAccuracy
    "high_density": 4,      # 4 = HighDensity
    "medium_density": 2,
}
```

### 4.2 全局约定（新增）

**在 pipeline 运行期间，禁止调用 `sensor.get_supported_options()`。**

需要了解 sensor 能力时，两种安全做法：
1. 使用硬编码的 `rs.option.*` 常量（推荐）
2. 先 `pipe.stop()`，再枚举，再 `pipe.start()`

### 4.3 影响范围审计

```bash
$ for f in *.py; do grep -c "get_supported_options" "$f"; done
rs_filter_compare.py : 1 处（已修复）
其他脚本            : 无
```

- `rs_anomaly_probe.py` 中的 1 处是**注释**（说明为何不用）
- `rs_stream_test.py`、`rs_mdr_probe.py`、`rs_precision_probe.py`、
  `rs_capture.py`、`rs_neck_probe.py`、`rs_live_view.py` 均无此调用

**因此受影响的历史数据仅限 `rs_filter_compare.py` 第一次运行的那一行**
（即 `30fps 848x480` 无滤波配置的 45.015mm）。

## 5. 对既有结论的影响评估

| 结论 | 是否受影响 | 说明 |
|---|---|---|
| 「temporal 把 MDR 从 45mm 改善到 1.65mm，改善 27×」 | ⚠️ **受影响，需修正** | 分母 45mm 是污染值。以干净值 ~2.8mm 计算，改善约 **1.7×**，而非 27× |
| 300-500mm 区间 MDR 1.38-3.39mm | ✅ 不受影响 | 来自其他脚本 |
| 距离衰减曲线（500mm 后跳变） | ✅ 不受影响 | 来自 `rs_mdr_probe.py` |
| 时间平均收益（16 帧 → 0.87mm） | ✅ 不受影响 | 来自 `rs_mdr_probe.py` |
| 5 轮重复性 1.2-1.7× | ✅ 不受影响 | 独立脚本 |
| 误差非相机振动（箱间相关 +0.015） | ✅ 不受影响 | 来自 `rs_mdr_probe.py` |

### 修正后的滤波器收益

Sol 质疑「27× 不可信」，实测确认 **Sol 是对的**，但原因不是它推测的
统计偏差，而是我的分母用了污染数据。

| 配置 | 0-300mm MDR | 相对无滤波 |
|---|---|---|
| 无滤波（干净值，来自 `rs_mdr_probe`） | 2.756 mm | 1.0× |
| temporal 强 α=0.1 | 1.646 mm | **1.67×** |
| spatial + temporal | 2.046 mm | 1.35× |

**修正结论：temporal 滤波的收益约 1.7×，不是 27×。**
它仍然是最优配置，但不是「数量级改善」。

## 6. 待验证项

本次定位基于「二分测试 + 因果链推理」，尚未做的确证实验：

**实验：显式复现**
```
A. 启动 pipeline → 调用 get_supported_options() → stop()
   → 立即采 300 帧 → 测 MDR   【预期：显著高于正常值】
B. 启动 pipeline → 不调用 → stop()
   → 立即采 300 帧 → 测 MDR   【预期：正常值】
```
若 A 显著高于 B，则根因确证。

`rs_anomaly_probe.py` 已具备执行该实验的能力（支持 `--record` 存原始数据 +
`--analyze` 用三套独立逻辑交叉验证）。

## 7. 方法论教训

1. **Sol 的质疑方向是对的，具体机制猜错了。** 它推测是 temporal 制造的
   时间相关性导致统计偏差，实测自相关仅 +0.05 左右，不成立。但它坚持
   「先查明异常再比较滤波优劣」这个顺序是**完全正确的** —— 若跳过这一步，
   我会一直用错误的 27× 数字做方案设计。

2. **单一脚本的结论必须交叉验证。** 这个 bug 存在了很久没被发现，是因为
   我一直在用同一个脚本重复测。`rs_mdr_probe.py` 的存在才让差异暴露。

3. **API 的"只读"调用也可能有副作用。** `get_supported_options()` 语义上是
   查询，实际会阻塞数据流。这类陷阱只能靠实测发现。
